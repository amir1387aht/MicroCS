# Offline preview-bundle verification

From a trusted MicroCS source checkout, use Python 3 (standard library only):

```sh
python3 tools/verify_preview.py /path/to/MicroCS-2.0.0-preview.1-g0123456789ab
```

Pass the **single bundle directory** generated by `tools/package_preview.py`,
not its parent directory or an archive. No build, installation or network access
is required. The verifier reads files only: it does not extract or inspect archive
members, execute binaries, import code from the bundle, download anything or
modify the bundle. Filesystem access times may change as a consequence of reads.

Optionally require independently obtained expected identifiers:

```sh
python3 tools/verify_preview.py /path/to/bundle \
  --expected-commit 0123456789abcdef0123456789abcdef01234567 \
  --expected-version 2.0.0-preview.1
```

The commit must be the **full lowercase 40-hex Git identifier**, not a short hash,
branch, tag or ref. The version must follow the current preview naming policy:
`2.0.0-preview.N`, with a positive integer N without leading zeroes. Expected
values must come from a separate source if they are to provide an independent
comparison; copying them from the supplied manifest adds no independent evidence.

## What a successful check means

The current `microcs-preview-manifest` **version 1** emitted by the packager is
supported. The verifier deliberately rejects missing/unknown manifest fields and
other schema versions instead of guessing forward compatibility. It checks:

- Preview channel, matching package/runtime version, full lowercase commit/tree
  identifiers, integer epoch, no-firmware flag and current packaging-environment
  field types. This validates metadata structure, **not the truth of those claims**.
- Exactly the source `.tar.gz` and Studio `.zip` archives, plus the Linux x64
  `.tar.gz` archive if and only if the manifest host is `linux-x86_64`. Names must
  match `MicroCS-{package_version}-g{first 12 commit characters}-{kind}` with the
  packager's suffixes: `source.tar.gz`, `studio.zip`, `linux-x64.tar.gz`.
- Null host capabilities when no host is included; otherwise a string list
  containing the packager's required `capabilities=1`, `Compiler=1`, `TFT=0` and
  `LVGL=0` lines. **The verifier does not run the host or validate its capabilities.**
- An exact `SHA256SUMS` inventory: every listed archive and `manifest.json`, with
  no duplicates or other checksum records. Each record uses a lowercase 64-hex
  SHA-256 digest, two spaces and a simple filename (LF or CRLF line endings).
- Manifest checksum, archive byte sizes and streaming SHA-256 digests agreeing
  with both manifest and checksum records.
- Exactly those files plus `SHA256SUMS` in the directory. Extra files/directories,
  duplicate JSON keys, malformed JSON/UTF-8, nonstandard JSON numeric constants,
  unsafe filename references, symlinks and nonregular input files are rejected.
  Each metadata file has a 1 MiB maximum; archives are hashed in 1 MiB chunks.

Keep the bundle unchanged during verification. Ordinary detectable file changes
are rejected, but this is not a transactional snapshot or a guarantee against
concurrent filesystem manipulation. The bundle directory itself must not be a
symlink; this does not certify the ancestry or trustworthiness of its filesystem.

## Exit codes and diagnostics

- **0:** verification passed. Standard output starts with `VERIFIED:` and reports
  package version, full commit and archive count, followed by the limitations.
- **1:** verification or local I/O failure. Standard error starts with `ERROR:`;
  no success output is printed. Missing/unreadable files, inconsistent metadata,
  unsupported schemas and digest/size mismatches all fail.
- **2:** invalid command-line usage, including invalid expected identifiers.
  Standard error includes argparse usage/error text. `--help` exits 0.

If verification fails, do not use the bundle on that basis. Obtain a fresh bundle
from your intended source, confirm the expected identifiers independently, or
investigate the mismatch without executing its contents. Do not “repair” supplied
checksums merely to make the check pass.

## Important limitations

**Checksums are not signing or publisher authentication.** Someone replacing both
archives and metadata can produce an internally consistent bundle. Expected
commit/version comparison also does not prove that archive contents came from
that commit, or that the publisher is trustworthy.

No archive member names/content, source tree contents, ELF architecture, binary
behavior, offline Studio completeness, firmware absence, capability truth,
security posture or compatibility are independently inspected. A successful
result guarantees neither safe extraction nor safe execution. Use trusted source
and compatible compiler-generated images; the runtime is not a sandbox. This CLI
is an integrity/metadata check, not the existing extracted-candidate smoke tests
or release approval, and it does not tag, publish or install anything.

Run its own fixture tests with:

```sh
python3 -B tests/test_verify_preview.py
```

Tests include opaque ordinary local archive-byte fixtures (hostless/host-present),
a genuine hostless packager output from a temporary committed repository, altered
and missing data, coverage/schema failures, expected-value mismatches and
read-only input checks. They do not execute binaries or extract archives.
